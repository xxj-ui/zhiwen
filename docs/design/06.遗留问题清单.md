## 10. B13：文档更新口径（待决策，2026-11-02 定为「先不做，仅登记」）

**背景**：当前"更新"只有一条隐式路径 —— **同名重传**（`POST /api/documents/upload`，靠 `uq_documents_filename_lower` 判同名 → `overwritten=true`）。它带来三个用户侧痛点：

1. 必须把新文件名改成与旧文件**完全一致**（大小写不敏感），否则会新增一篇文档；
2. 改名 / 改扩展名不算更新，旧文档需手工删除；
3. 无版本历史，误覆盖不可恢复（`03` K-10 明确版本管理在本期范围外）。

| 路线 | 做法 | 影响面 | 工作量 | 主要风险 |
| --- | --- | --- | --- | --- |

## 13. B16：BM25 索引预热（2026-11-04）

**问题**：导入大知识库后，第一次提问要等 BM25 全量重建（8,935 片段实测 **8.62 s**，0.97 ms/块、48 万字/秒），第二问起才正常。

**做法**

| 项 | 落点 | 说明 |
| --- | --- | --- |
| 导入后同步重建 | `services/indexing.rebuild_bm25` + `api/routes/documents.py` | 整批文件处理完、**重建完成后才返回**：返回"成功"即"可检索" |
| 整批只重建一次 | 同上 | N 个文件逐个提交会付 N 次全量成本 → 前端改为整批提交（`uploadMany`，1~20 个） |
| 删除后台合并重建 | `services/indexing.warm_in_background` | 删除响应不等重建；1.5 s 合并窗口内连续删除只重建一次 |
| 兜底 | `rag/bm25_index.ensure_built` | 预热失败只记日志，检索路径仍懒重建；`rebuild()` 与 `ensure_built` 共用 `_build_lock`，并发不会双建 |
| 度量 | `bm25_index.last_build_seconds` | 日志 `BM25 预热完成 chunks=… 构建=…s 排队=…s`，把构建与排队分开记 |

**实测（真 PG 8,935 片段 / 真 MinIO / 真 DeepSeek）**

| 场景 | 改前 | 改后 |
| --- | --- | --- |
| 单文件导入后第一问 | 等一次全量重建（≈8.6 s） | 上传 8.5 s（含重建）→ 第一问 **2.20 s** |
| 3 文件整批导入后第一问 | — | 上传 8.4 s、日志仅 1 条重建 → 第一问 **1.05 s** |
| 连续删 3 个文档 | 0.01~0.13 s，之后首问重建 | 0.06/0.01/0.01 s，后台 1 条重建（构建 8.3 s、排队 0.0 s） |

**已知行为（非缺陷）**

1. 删除后 1.5 s 合并窗口 + 重建期间提问会等这一次重建（约 8 s）；导入路径不再有该等待。
2. 一次导入若跨越多个请求（用户分批传），每批各重建一次。
3. 重建失败（如更新代码后 `last_build_seconds` 缺失）曾导致"已入库却返回 500" —— 已修：预热整体包在 try 内，任何异常只记日志。**教训：写操作的响应不能依赖预热成功。**

**追加：脏读修复（2026-11-04）**

原实现里 `generation` 变化只阻止"装进缓存"，但**仍把作废快照 return 给调用方**——提问恰好撞上并发写入时，会用一份可能包含已删除文档的旧索引作答，且下一个请求还要再建一次（8.6 s × 2）。

改法（`Bm25Index._build_fresh`）：

| 情形 | 行为 |
| --- | --- |
| 构建期间无写入 | 一次构建，装入缓存 |
| 第 1 次构建期间有写入 | 丢弃 + 记 warning + 立即重试 |
| 第 2 次仍有写入 | 只把最后一次结果应急返回给本次调用，**不缓存**；下一次调用重新构建 |
| 构建抛异常 | 向上传播（不重试、不吞），由 `services/indexing` 兜底记日志 |

单测 `scripts/test_bm25_generation.py`（不依赖 DB/模型，用 `fetch_all` 里调 `invalidate()` 制造竞态）：**16 项断言全通过** —— 正常路径只建一次、撞一次写入重试并缓存新数据、两次都撞不缓存、`rebuild()` 同样重试、异常正常抛出。真机回归：上传 9.0 s（含重建）→ 第一问 2.68 s。

**未做**

- BM25 增量更新（只增删受影响文档），仍是全量重建；语料再涨一个量级（几万片段）要重新评估。
- 索引落盘缓存（重启后秒加载）；当前靠启动预热（8.9 s）+ 导入预热覆盖。

## 15. B18：扫描件 OCR 兜底（2026-11-06）

**背景**：个人自用场景的最后一个硬缺口——`load_pdf` 抽不到文字层就整页丢弃，扫描件 PDF 导入后是空文档。SRS v0.14 原本把「不含扫描件」写进范围，本次随实现一并回写为 v0.15。

**选型（按总增量与中文效果排序，体积为 PyPI wheel 实测 + 拆包核对）**

| 方案 | 依赖 | 模型 | 中文 | 结论 |
| --- | --- | --- | --- | --- |
| **RapidOCR + pypdfium2** | rapidocr 14.9 MB + onnxruntime 14.9 MB + pypdfium2 3.9 MB | 随 wheel 自带 16.2 MB（PP-OCRv4 det 4.7 / rec 10.9 / cls 0.6） | 好 | **采用**：纯 CPU、不引 torch/paddle |
| PaddleOCR | paddlepaddle 104.8 MB | 16 MB | 最好 | 放弃：依赖重、版本兼容易出事 |
| EasyOCR | 已有 torch | ≈100 MB（估计） | 中上 | 放弃：中文不如 PP-OCR、CPU 慢 |
| Tesseract | 需装 exe + 中文包 2.5~13.1 MB | — | 一般 | 放弃：表格/竖排差，且要装系统程序 |

本机实际增量 **≈26 MB**（rapidocr 17 MB + pyclipper 2 MB + shapely 7 MB）；onnxruntime / opencv / pypdfium2 / numpy / pillow 环境里本来就有。

**实现**（`server/rag/loaders.py`）

- `load_pdf` 逐页判断：`extract_text()` 少于 `ocr_min_chars`（默认 10 字）→ 用 pypdfium2 按 `ocr_dpi`（默认 120）渲染该页，交 RapidOCR 识别后并入该页文本。
- 引擎是进程级单例（`RapidOCR(use_cls=False, intra_op_num_threads=8)`），首次遇到扫描页才加载，约 0.6 s；带文字层的 PDF 完全不受影响。
- 单页 OCR 失败只告警并跳过该页，不让整份文件失败。
- 参数集中在 `core/config.py`：`RAG_OCR` / `RAG_OCR_DPI` / `RAG_OCR_MIN_CHARS` / `RAG_OCR_MAX_PAGES`。

**实测**

| 项 | 结果 |
| --- | --- |
| 识别质量（436 字对照） | 150 dpi 相似度 0.947 / 120 dpi 0.992 / 200 dpi 0.990（关方向分类后 150 dpi 升到 0.991） |
| 单页耗时 | 首屏 2.9 s（含引擎加载），之后 1.09~2.07 s/页 |
| 引擎内存 | +40 MB |
| 3 页扫描件整链路（上传→切分→嵌入→BM25 重建） | **6.5 s**，产出 3 块，正文可读 |
| 带文字层 PDF | 0.09 s，零 OCR 调用 |
| 开关验证 | `ocr=False` → 0 页；`ocr_max_pages=1` → 只识别第 1 页 |

**已知代价与未做**

- 扫描件导入变慢：约 **+2 s/页**，50 页扫描件仅 OCR 就要 ~100 s，已超 NFR-1 的 60 s；超长扫描件建议设 `RAG_OCR_MAX_PAGES`。
- 表格、竖排、手写未验证（当前样本是规整排版）；双栏版面可能串行。
- OCR 专项用例已补：`07.测试用例清单` v0.12 的 TC-43~TC-47（OCR 生效 / 关闭开关 / 页数上限 / 混合文档 / 文字层回归），5 条均已实测（TC-44/45 只到 loader 层）；仍无 CI 回归。

## 16. B19：BM25 索引去掉分词副本（2026-11-06）

**起因**：追问「可撑规模为什么只有 1.5 万块」。实测把瓶颈定位到 BM25 而非 pgvector（HNSW 索引本来就在，vector 0.8.5）：构建 **0.77 ms/块**、常驻 **≈16 KB/块**、查询 **0.28 µs/(块·词)**，三条都随块数线性增长，而每次上传都要全量重建并阻塞响应。

**改动**（`server/rag/keyword_search.py`）：`__init__` 不再把全量分词结果存进 `self._tokenized`，改为逐块分词后立即生成 `_tf` / `_doc_len` / `_df`，分词列表用完即弃。`search()` 本来就只用 `_tf` 与 `_doc_len`，**打分逻辑零改动**。

**实测**（8,960 块 / 468 字每块；tracemalloc，两个独立进程各量一次）

| 实现 | Python 堆常驻 | 每块 | 构建期峰值 |
| --- | --- | --- | --- |
| 保留 `_tokenized`（旧） | 184.0 MB | 21.0 KB | 184.1 MB |
| 不保留（新） | **125.8 MB** | **14.4 KB** | **125.8 MB** |
| 差值 | **-58 MB（-32%）** | -6.6 KB | -58 MB |

等价性：同一份语料、10 条查询 × top-10（100 个命中）逐位比对，**id 与分数（保留 10 位小数）完全一致**；`scripts/test_bm25_generation.py` 16 项断言全通过；重启后预热 11.1 s、BM25 就绪 280 块、`/api/health` 全绿。

**教训（口径）**：先前按「构建阶段 RSS 增量」把内存拆成 `_tokenized 172 MB / _tf 27 MB`，据此得出「分词副本占 86%」——这是**错的**。分词产生的 str 对象被 `_tf` 的 Counter 键共享，两个阶段复用同一批内存，增量归因会严重错配。正确做法是 **tracemalloc + 每个变体单独起进程**，得到的是 32%。

**后续**：本节改动已在 v0.28 被整体替换 —— 索引结构不再由本项目维护（改用 bm25s），下面的「未做」只剩查询剪枝仍成立。

**未做（下一步，按性价比）**

- 查询仍全量扫描（§17 后已在 numpy 层完成，仍与块数线性）：O(块数 × 查询词数)，10 万块 + 15 词问题约 430 ms → 需查询剪枝或倒排。
- 重建仍全量且阻塞上传：10 万块约 77 s → 需按 `document_id` 增量更新。
- 内存剩余大头是每块的 `Counter`（≈10 KB/块），只能靠倒排结构再降。

## 17. B20：BM25 两处改造暂缓（2026-11-06，仅登记）

**起因**：追问「整个项目的检索性能瓶颈是不是卡在 BM25 的实现方式」。为把「在线延迟」与「规模能力」两件事分开，重新量了一遍分段耗时。

**实测（2026-11-06，本机 16 核，只读探针；池化链路，与运行期一致）**

| 阶段 | 280 块（真实语料，中位） | 8,960 块（同批文本合成，中位） | 随块数 |
| --- | --- | --- | --- |
| `embed_query` | 10.20 ms | 10.20 ms | 常数 |
| dense `search` | 7.16 ms（EXPLAIN：seq scan） | 4.04 ms（HNSW，B17 实测） | 亚线性 |
| BM25 `search`·4 词 | 0.18 ms | **9.53 ms** | 线性 |
| BM25 `search`·14 词 | 0.85 ms | **31.12 ms** | 线性（×词数） |
| BM25 构建 | 217 ms | **6,509 ms**（0.73 ms/块） | 线性 |
| `rrf_fuse` | 0.018 ms | 0.018 ms | 常数 |
| `retrieve` 整条 | 18.35 ms | ~31 ms（短问题，B17 实测 8,935 块） | — |

**归因**

1. **在线延迟**：280 块时 BM25 占 4%（嵌入 56% / dense 39%）；到 ~9 千块 BM25 反成最大单项（14 词问题 31 ms > 嵌入 10 ms + dense 4 ms）。`services/chat.retrieval_query` 会把上一轮问题（截 200 字）拼进 query，续聊时词数常翻倍到 20~30 → BM25 60~70 ms，是唯一随「多轮」线性恶化的环节。
2. **端到端**：检索全链路 18~31 ms 对 LLM 首字节 1.64 s 只占 1~2%；上传链路的 CPU 嵌入（111 ms/块）也不经过 BM25。**用户可感知的瓶颈不是检索。**
3. **规模能力**：0.73 ms/块的全量重建（8,960 块 6.5 s）每次上传都要付一次并阻塞响应，10 万块约 77 s；常驻 14.4 KB/块、8,960 块 126 MB。这一条由 BM25 的实现方式（全量重建 + 每块 Python `Counter` + 查询全量扫描）直接造成，pgvector 侧没有同类问题。

**决策（2026-11-06，你已拍板）：暂不改，仅登记。** 触发条件任一命中再启动：

| 触发条件 | 阈值 | 为什么是这条 |
| --- | --- | --- |
| 语料规模 | 块数 > 1.5 万 | 按 0.73 ms/块、3.5 µs/(块·14 词) 线性外推，1.5 万块 ≈ 11 s 重建 / 52 ms 查询 |
| 导入形态 | 单次导入 > 50 文件，或要求导入响应 < 5 s | 全量重建成本直接落在上传响应里 |
| 检索延迟 | BM25 `search` p95 > 50 ms | 进入与 LLM 同一量级之前的最后安全线 |
| 内存 | 索引常驻 > 300 MB（约 2 万块） | 单 worker 独占，多 worker 会按进程翻倍 |

**触发后的两刀（彼此独立，可只做后者）**

| 改造 | 落点 | 效果 |
| --- | --- | --- |
| 倒排 postings | `rag/keyword_search`：`term → [(doc_idx, tf)]`，查询只扫命中文档 | 查询 O(块数×词数) → O(命中块)；顺便去掉每块的 `Counter`，内存再降 |
| 按 `document_id` 增量 | `rag/bm25_index` + `services/indexing` | 把全量重建从上传/删除路径拿掉，重建成本从 O(N) 降到 O(受影响文档) |

**口径与失效条件（避免误引）**

- 8,960 块那列是**合成语料**：把库里的 280 块真实文本复制 32 份（平均 468 字/块与真实一致，总 419 万字），只用于量扫描成本；df 分布被压缩、命中块数偏多，故为**偏上限值**，真实语料低 10~30%。结果质量不可引用。
- 4.04 ms / 31.1 ms 两处引自 §14 B17 的 8,935 块实测，非本轮；本轮未重建该规模的真实库。
- 小语料下 dense 反而更慢（7.16 > 4.04 ms）是规划器选择：280 行时走 seq scan（EXPLAIN 已确认），8,935 行时才用 HNSW。
- 复跑：`probe_retrieval_pool.py`（分段）、`probe_bm25_scale.py`（规模）。

## 17. B20：关键词检索改用 bm25s（2026-11-06）

**背景**：追问「用现成库会不会更好、是不是重导知识库就行」。实测四个实现（同一语料、同一 jieba 分词、8,960 与 35,840 块两档）：

| 实现 | 查询 P50（5/15/52 词，35,840 块） | 索引内存 | 检索质量 |
| --- | --- | --- | --- |
| 自研（逐块 Counter） | 59.5 / 156.7 / 348.0 ms | 8.9 KB/块 | 基准 |
| rank_bm25 | 48.5 / 137.2 / 598.2 ms | 3.2 KB/块 | top-5 与基准一致 |
| **bm25s** | **0.4 / 0.9 / 1.2 ms** | **1.1~2.0 KB/块** | top-5 4/5（并列名次取法不同） |
| SQLite FTS5 | 13.5 / 63.6 / 236.0 ms | ≈0（落盘） | top-5 与基准一致 |

结论：**检索质量不因换库而提升**（BM25 是公式），换库改的是成本曲线。用户裁决「只替换 + 等价性验证」。

**不重导知识库**：BM25 索引是派生结构，启动时由 `rag_chunks` 现算，换实现只需改代码 + 重启；重新导入只会白付一轮嵌入与重建。

**实现**（`server/rag/keyword_search.py`）

- 内部改为 `bm25s.BM25(k1=K1, b=B, method="lucene")`，`index()` 时喂**本模块 jieba 分好的词**（bm25s 自带切分对中文无效）。
- `search()` 用 `get_scores()` 拿全量分数，再 `nonzero(score>0)` + `np.lexsort((块序, -分数))` 取 top_k —— 保住旧实现的两条语义：**只回命中块**、**同分按块序稳定**。
- 对外契约（返回字段、`size`、异常）不变，`services/retrieval.py` 与 RRF 无需改动。

**等价性实测**（真实 280 块、20 条真实问题）

| 项 | 结果 |
| --- | --- |
| top-10 序列 | **20/20 条完全同序**（不只是重合，是顺序一致） |
| 最低重合度 | **100%** |
| 无命中行为 | 「量子纠缠拓扑绝缘体」「空查询」两边都 0 条；含泛词的问题两边都回 10 条 → 零分过滤一致 |
| 分数 | bm25s 分数 = 旧分 × **0.4**（= 1/(k1+1)）恒定缩放；RRF 只用名次，链路无影响 |
| 单测 | `scripts/test_bm25_generation.py` 16 项全通过 |
| 全链路 | 重启后 `BM25 索引就绪 280 块`、预热 9.7 s；`POST /api/chat` 收到 `citations`（top1 chunk 8998 = BM25 top1）+ 450 个 `delta` + `done`，测试会话已删除 |

**上述三项已作废（2026-11-09）**

本节登记的「倒排 postings」与「按 `document_id` 增量重建」两刀**不再实施**——改走下一条更彻底的路线：
关键词检索整体下沉到 PostgreSQL（`content_tsv` + GIN），写放大与内存墙一次性消除，详见 §18 B21。

## 18. B21：关键词检索下沉到 PostgreSQL（2026-11-09，已落地）

**背景**：§17 的两条路（倒排 postings + 按 `document_id` 增量重建）都是在 bm25s 基础上打补丁。
根因是「进程内全量矩阵」这一数据组织方式不合场景——bm25s 面向静态语料，本项目是运行时持续写入：
每次上传要 O(N) 重建（0.73 ms/块）、每次查询 O(N) 全量打分、内存 14.4 KB/块且不随规模释放。

**决策**：整体下沉到 PostgreSQL——`rag_chunks.content_tsv` + GIN 倒排（V003 迁移），
写入随行生成、索引自动维护，进程内不再持有任何关键词索引。

**五个关键实现选择**

| 选择 | 为什么 |
| --- | --- |
| 分词留在应用层（jieba），PG 用 `simple` 配置 | 不引入 zhparser / pg_jieba（要编译，容器里没有）；分词规则与改造前逐字一致，避免索引与查询切法不一致导致静默检索不到 |
| 查询用 `to_tsquery` 手工拼 OR | `plainto_tsquery` 是 **AND** 语义，长问题退化为「所有词都必须出现」，实测只命中 0~1 条；BM25 是 OR 语义 |
| 加停用词表挡虚词 | `ts_rank_cd` 不做 IDF 加权，「的 / 有 / 哪些」几乎命中所有块并淹没关键词；BM25 靠 IDF 自动压到近零 |
| `ts_rank_cd` 而非 `ts_rank` | cover density 计入词距，「三次握手」这类中文短语更贴合 |
| 检索两路复用同一连接 | 池每次出池要探活（实测 ~5 ms），分两次取就是两次往返 |

**实测（本机，2026-11-09）**

| 项 | 结果 | 口径 |
| --- | --- | --- |
| 8,680 块 · 低 df 查询（899 命中） | **6.56 ms** | 合成语料（280 块 × 32 份），GIN 倒排 |
| 8,680 块 · 高 df 查询（4,464 命中，51%） | 54.5 ms | 回表成本主导；此时优化器改选 seq scan（77 ms） |
| 280 块 · 检索全链路 | 38~44 ms | embed 25.6 + dense 13.2 + keyword ~5；本机负载偏高，B20 同口径基线 18.4 ms |
| 存储 | **2.8 KB/块**（8,680 块：heap 11 MB + GIN 2.76 MB） | 落磁盘，不占进程内存（bm25s 为 14.4 KB/块内存） |
| 上传写入 | **0 重建** | 索引由 PG 随 INSERT 维护 |

**代价（避免误引）**

- 280 块这种小语料，查询比 bm25s 慢约 20 ms：SQL 有固定开销，数据少时优化器走 seq scan。
- 高 df 查询（>50% 命中）退化到 50 ms 量级——倒排的固有特性，Lucene 同样如此，需靠停用词与查询剪枝缓解。
- 收益要到几千块以上才兑现；当前规模属于「为将来埋单」。

**验收**：3 条真实问题 top-1 全部命中正确段落（线程池参数 / 三次握手 / 索引失效）；
存量 280 块经 `scripts/backfill_tsv.py` 回填，`count(content_tsv)` = 280。

**回滚路径**：`V003__chunk_tsvector.rollback.sql` 删列与索引，代码侧 revert 对应提交即可恢复 bm25s。
